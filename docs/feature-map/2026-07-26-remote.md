# xyz-agent 远程化功能地图

**日期**: 2026-07-26 | **基准分支**: feat-remote-use | **状态**: P1 桌面远程模式已交付（commit `4289fefe`，2026-07-26）；P0 服务端远程化 + P2+ 协同阶段按原规划演进

> 本文档记录 xyz-agent 远程化能力的完整架构方案。需求：服务器跑软件本体（runtime + pi），客户端（桌面 Electron / 手机浏览器 / 手机 APP）连服务器使用，支持多客户端同时连接和操作。

---

## 一、需求与决策

### 1.1 核心需求

1. 服务器上跑软件本体，客户端 APP 连接服务器，pi 运行在服务器
2. 手机端浏览器能当客户端连接服务器，执行基本功能
3. 本地和远程可同时连接和操作服务端（多客户端协同）

### 1.2 已确定的决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| **文件系统作用域** | 模式 A：项目在服务器 | pi 操作服务器本地 fs，FileService/GitService 零改造；客户端通过 git 维持两端一致 |
| **部署形态** | 自托管单机（一用户一实例） | 不背多租户包袱；实例隔离机制支持未来扩展 |
| **认证机制** | 服务端发 token，客户端持 token 连接 | 自托管够用；WSS + token + Origin 校验 + 反代限流 |
| **移动 APP 技术栈** | Capacitor 套壳 | 一套移动端 Vue 代码同时出手机浏览器版和 APP 版，复用现有技术栈 |
| **桌面 Electron 定位** | 保留双模式（本地 + 远程） | 现有桌面用户零感知，远程用户也有桌面 APP 体验 |
| **客户端 Web 形态** | 移动 Web 独立于桌面 renderer | 移动布局与桌面布局差异大，各做各的 |
| **协同强度** | 看共享 + 操作互斥（默认假设） | pi 是单例，物理上不能被并发驱动；多端共享对话流是核心价值 |
| **身份模型** | 单用户多设备（默认假设） | 自托管场景 token 即身份，多设备拿同一 token，无需账号体系 |
| **token 传递方式** | WS 首条消息鉴权（非 query string） | query string 会进反代 access log / Referer 泄露（OWASP 反对）；浏览器/Capacitor WebView 不能设 Authorization header，首条消息是全平台兼容且不进日志的最优解 |
| **pi 与连接生命周期** | 解耦：客户端断开 pi 继续跑（默认假设） | AI agent 单次对话跑几分钟，移动端随时断；业界共识（MS Agent Framework / Anthropic harnesses）pi 与连接解耦，断开后跑到完成或显式取消 |
| **TLS 策略** | runtime 不内置 TLS，公网走反代 | runtime 内置 TLS 是独立复杂度（证书/SNI/续期），收益不抵成本；公网用反代、个人多设备用 Tailscale（WireGuard 加密）更干净 |
| **主要网络拓扑** | Tailscale（个人多设备）+ 局域网 IP + 公网反代 | 三种拓扑覆盖自托管主要场景；公网直连 runtime 不推荐（无防护层） |
| **引导连接方式** | 服务端首启输出「连接字符串」+ QR，客户端粘贴/扫码/deep link 一键连接 | 避免手敲长 token；同时支持 `xyz-agent://` deep link（APP）和纯文本 URL+token（Web/微信转发） |
| **服务端分发形态** | 双轨主推：① npm 包 `@xyz-agent/runtime` + ③ Docker 镜像；② 单文件二进制 / ④ App headless 后续按需 | 三平台（Mac/Linux/Win）全覆盖；DMG/App 为桌面 GUI 设计不适合服务端（依赖 Electron 当 Node、体积大、Linux 装不了）；pi 三平台均支持 |

> 「协同强度」「身份模型」「pi 与连接生命周期」三项为合理默认（用户未明确选择时的推断），实施前需最终确认。

> **审查记录**（2026-07-26）：方案经 reviewer（内部代码盲点）+ researcher（业界参考）双路审查，发现 14 项关键技术遗漏，已补充到 §四/§八/§十，并新增 §十二「已知技术风险与对策」。详见 §十三 审查记录索引。

## 二、现状关键发现

### 2.1 runtime 天生是独立服务

ADR-0032 明确定位 runtime 为「零 Electron 依赖的纯 Node.js 服务」：

- `packages/runtime/src` 全量 grep `from 'electron'` **零命中**
- 启动只吃 env + argv：`node index.cjs --port=N` + 几个 `XYZ_AGENT_*` 环境变量
- pi 子进程是 runtime 自己 spawn 的（孙进程），不依赖 Electron
- 实例隔离机制（`XYZ_AGENT_DATA_DIR` + 端口偏移）已就位
- `/health` HTTP 端点已就绪，外部 supervisor 可对接

### 2.2 renderer 本质是纯 web SPA，业务层零 Electron 耦合

所有业务数据通路（聊天、文件树、git、worktree、配置）全走 WebSocket RPC。`lib/ipc.ts` 是唯一的 Electron 访问点，已做 `api?.xxx() ?? Promise.resolve()` 优雅降级——`window.electronAPI === undefined` 时业务照跑。

### 2.3 远程化硬阻塞点少

| 阻塞点 | 位置 | 性质 |
|---|---|---|
| WS 服务零认证 | `connection-manager.ts:56`（无 verifyClient） | 安全阻断 |
| 前端 WS 地址写死 `ws://localhost` | `useConnection.ts:214,239,265,270` | 连接逻辑 |
| `local-file://` 图片协议 | `DetailPane.vue:314` + `main.ts:183` | 唯一的 FS 硬绑定 |
| pi 二进制定位依赖 `process.cwd()` | `process-manager.ts:22`（打包模式） | 脱离 Electron cwd 后需配置化 |

其他 IPC（窗口控制、BrowserPane drawer、全局快捷键、多窗口 API）都是桌面增强，砍掉不影响核心 chat/file/git 流程。多窗口 API（`createWindow` 等）renderer 里零调用。

## 三、多客户端协同现状

### 3.1 已就绪（传输层架构干净）

| 维度 | 现状 | 证据 |
|---|---|---|
| WS 多连接 | 连接池 `Set<ws>`，无连接数限制，新连接不踢旧连接 | `connection-manager.ts:40,79-82` |
| 请求-响应隔离 | reply 点对点，A 的请求结果只回 A | `message-broker.ts:110-112` |
| 事件广播 | pi 流式、session 状态、终端输出、config 变更全广播 | `session-service.ts:762-770` 等 |
| session/pi 多实例 | `Map<sessionId, ManagedSession>`，每 session 独立 pi 进程 | `session-service.ts:80`、`process-manager.ts:121` |
| 多客户端共享同一 session | pi 进程是 session 级的，所有客户端操作同一 session 路由到同一 pi | `session-service.ts:758-789` |

### 3.2 阻断点（业务层"全局唯一"假设）

| 阻断点 | 现状 | 影响 |
|---|---|---|
| 连接身份缺失 | 连接完全匿名，ws 对象无法映射到稳定客户端 | 无法追踪"谁发了什么"、无法定向推送 |
| 操作互斥不可见 | isGenerating 是 session 级，busy 拒绝无差别广播给所有人 | B 发消息被拒时所有人看到提示，体验混乱 |
| 插件活跃 session 全局唯一 | ~~`ActiveSessionResolver` 返回 runtime 全局唯一 active session~~ **【已解决 P7】** `ActiveSessionResolver` 绑 clientId（四级 fallback：P5 activeSessions Map → lease busyOwnerId → 全局 isGenerating → null），plugin RPC handler 经 ALS `sessionContext.getStore()?.clientId` 透传；无 clientId（hook/定时器/生命周期）走全局 fallback 零回归 | ~~多客户端各有活跃 panel，插件拿到错误的 session~~ 已修复 |
| 前端无协同感知 | 单例 ws、单例 store，无"其他客户端存在"概念 | 看不到其他设备在线状态 |
| **消息无可靠投递层** | `message-broker.ts:59-88` broadcast 纯 fire-and-forget，无序号/无缓冲/无回放（grep `backfill/resume/lastSeq/cursor/replay/outbox` 零命中） | **断线期间消息永久丢失**：B 断线 10 分钟，期间 A 触发的 pi 流式增量/terminal 输出/config 变更，B 重连后全丢 |
| **pi 生命周期绑连接** | pi 单次对话跑几分钟，连接断开的处理语义未定义 | 若 WS 断 → pi 被 kill，移动端基本不可用；pi 等审批时所有客户端离线的处理未定义 |
| **除 pi 外操作全裸奔** | `isGenerating` 是唯一互斥；git commit 是 TOCTOU（`git-service.ts:226-254` 先 status 再 commit），config 是 last-write-wins，worktree 无 in-flight 去重 | 多客户端并发 commit 抢 `index.lock` 一个必失败；config 编辑静默覆盖；同名 worktree 并发一个失败 |
| **互斥机制简陋** | 用 `isGenerating` 布尔标志，无 TTL 租约 | 客户端 A 拿锁后崩溃/断网 → 锁永远不释放 → pi 卡死 |
| **Terminal 共享 PTY 冲突** | `terminal-service.ts` 一 session 一 PTY，多客户端 write/resize 打同一 PTY，attach 是 no-op | resize 冲突（最后生效）、输入交错、scrollback 丢失（重连看不到历史） |
| **远程删除 session 清理路径** | `session.delete` 只广播列表（`broadcastSessionList`），其他客户端 panel 的 store 分区清理依赖本地 deleteSession 流程 | B 正打开被删 session 的 panel，store 分区泄漏，后续操作 404 |

**关键洞察**：传输分发层（最难改的部分）已经就绪。真正阻断集中在**身份缺失**、**可靠投递层缺失**、**pi 生命周期耦合**和几个"全局唯一"业务假设。补 clientId 通道 + 消息序号缓冲层是解锁后续所有改造的前提。

### 4.1 协同语义

```
Sessions: Map<sessionId, ManagedSession>
├─ Session A (pi 进程 A)  ← 多设备共享
└─ Session B (pi 进程 B)  ← 多设备共享

Connections: Map<clientId, ws>
├─ clientId:mac-zsh  (桌面 Electron)
├─ clientId:iphone-safari (手机浏览器)
└─ clientId:iphone-app (手机 APP)

每设备的"活跃 session"独立记录:
activeSessions: Map<clientId, sessionId | null>   // 【R1-M4 命名统一】字段名复数，value 含 null（看非 session 视图时）
```

**核心规则**：
1. **session 是共享资源**：所有设备看到同一份对话流、文件树、git 状态（runtime 已支持，零改造）
2. **pi 是单例**：同一 session 只有一个 pi 进程，多设备同时发消息触发 busy 拒绝
3. **每设备独立活跃 session**：桌面看 session A 时，手机可以看 session B，互不干扰
4. **操作互斥可见**：某设备正在跟 pi 对话时，其他设备看到「Mac 正在操作 Session A」提示
5. **pi 与连接解耦**：客户端断开时 pi 继续跑到完成或显式取消（业界共识，AI agent 远程化必需）
6. **消息可靠投递**：所有广播消息带单调递增 seq，客户端断线重连用 lastSeq 拉缺失

### 4.2 应用层会话协议（WS 之上的可靠投递层）

**问题**：当前 `message-broker.ts` broadcast 是纯 fire-and-forget，客户端断线期间的消息永久丢失。多客户端共享 session + 移动端易断线，必须补可靠投递层。

**业界标准五件套**（websocket.org / Supabase / Azure / OneUptime 多源一致）：

| 组件 | 说明 |
|---|---|
| 服务端单调递增 seq | 每条广播消息打**全局单调 seq**（reply 与 initial state 点对点不打 seq）；envelope 顶层 `seq?: number` |
| 客户端 lastSeq | 客户端内存维护最后处理的 seq（**不持久化**：页面 reload 后 stores 全空，带旧 lastSeq 反而得到残缺状态；同页面生命周期内的重连才携带） |
| 服务端 ring buffer | **per-session 分桶**：`Map<sessionId, SessionBuffer>`，按 `payload.sessionId` 路由——有 sessionId 的消息（`message.*`/`session.*`/`terminal.*`/`extension.ui_request` 等）入对应桶，无 sessionId 的全局消息（`config.*`/`model.*`/`workspace.*` 等）不入桶。每桶独立条数/字节双限 LRU 驱逐 |
| 握手带 lastSeq | 重连时客户端 auth 消息传 lastSeq+bootId+`subscribedSessions`（客户端持有分区的 session 列表），服务端 `getReplayPlan` **只遍历订阅的 session 桶**收集 seq>lastSeq，按全局 seq 升序合并回放。限定范围避免回放未订阅 session 的消息（前端 chatSessions 是懒创建分区，回放未打开 session 会创建僵尸分区） |
| 缓冲驱逐兜底 | 缓冲已被 LRU 驱逐（lastSeq < 全局 evictedWatermark）或 bootId 不匹配（runtime 重启）→ `auth.ok {seqReset:true}` → 客户端 `location.reload()` 冷启动全量重建（renderer 无全局 reset 能力，reload 是构造性正确路径）。session 销毁清桶不推进 watermark（客户端收到 session.deleted 已清分区） |

**实现要点**：
- seq 是全局单调（不是 per-session），但 buffer 按 sessionId 分桶存储——「全局 seq + per-session 分桶」组合：回放时多桶按 seq 合并即得全局序
- terminal 输出（`terminal.data`）单独做 scrollback ring buffer，attach 时回灌最近 N 行（当前 attach 是 no-op，必须补）；terminal.data 打 seq 但不入 session 桶
- **全局消息（config.* 等）不入桶**：resume 路径下断线期间的全局增量会丢失（已知取舍）——前端重连补拉（P1 §6.4 现状 workspace.load/extensionApi.scan）+ 冷启动 initial state 覆盖大部分场景；全局消息大多是配置态（有 RPC 可主动拉取）或瞬态事件（send.rejected 的 busy 通知，过时无意义）
- config 时序态（busy/idle 翻转）无法靠初始快照重现，需要 presence 全量重推
- 短期可接受跨客户端无严格总序（单连接内顺序由 Node 单线程保证），长期若需要严格一致再引入 fencing token（**注意：seq 不能复用为 fencing token**；**审查修正**：P5 原计划引入 fence 但 P5-P7 无消费方，按 YAGNI 推迟到真正需要「跨客户端因果序」或「带版本校验的写入保护」时再设计。feature-map §十二.5 的长期方案标注推迟）

**SSE 备选方案**（未采纳，记录备查）：pi 输出主要是 server→client 单向流，SSE 原生支持自动重连 + `Last-Event-ID` 续传，能省掉自研五件套。代价是引入第二种传输（上行仍需 WS/HTTP）。当前倾向统一用 WS + 自研五件套，保持协议一致性；若实施时五件套工作量超预期，再评估 SSE。

### 4.3 客户端代码复用关系

Capacitor 本质是"web app 套原生壳"，所以移动 APP = 移动版 web 代码 + Capacitor 包装。客户端实际有两套 renderer：

| Renderer | 跑在哪 | UI 形态 | 复用方式 |
|---|---|---|---|
| `packages/renderer` | Electron | 桌面布局（现有） | 现状，加远程模式分支 |
| `packages/mobile-renderer` | 手机浏览器 / Capacitor | 移动布局 | 新建，可独立 web 部署 |

**共享层抽取策略**（长期方案，分两步）：
- 第一步：mobile-renderer 独立跑通（验证远程链路）
- 第二步：抽 `packages/core` 共享 stores/api/composables 非桌面部分

**可共享**：`api/`（WS RPC 封装）、`stores/` 非桌面部分、`composables/` 非桌面部分、xyz-ui 组件库

**不能共享**：`shell/` 布局入口、`electronAPI` 适配层、BrowserPane drawer、TrafficLight、窗口控制

## 五、认证流程

```
1. 服务端首次启动
   runtime 生成 32 字节随机 token
   写入 ~/.xyz-agent/token（权限 0600）
   终端打印：
     xyz-agent server started
     URL:   wss://your-server.com
     Token: a3f8b2c1...
   (并打印 QR 码：xyz-agent://connect?host=...&token=...)

2. 客户端首次连接（首条消息鉴权）
   手输 token，或扫 QR
   客户端存 token 到本地（Keychain/Keystore for APP，localStorage for Web）
   连接: new WebSocket(url)  // URL 不带 token，避免进日志/Referer
   连接建立后立即发送首条鉴权消息：
     { type: 'auth', token, clientId, deviceName, lastSeq }
   runtime 校验 token：
     失败 → close(4001) 并不纳入心跳/广播池
     成功 → 注册 clientId，回放 lastSeq 之后的缓冲消息，推送 initial state

3. 后续连接
   客户端复用本地 token + clientId，无需重新输入

4. 重置 token（设备丢失等）
   服务端跑 runtime --reset-token
   旧 token 失效，所有客户端需重新连接
```

**token 传递方式选择**（审查后修正）：
- **WS 首条消息**（采纳）：全平台兼容（浏览器/Capacitor WebView 不能设 Authorization header），token 不进 URL/日志/Referer，连接建立前可立即关闭非法连接
- ~~query string~~（否决）：token 会进反代 access log、浏览器 history、Referer（OWASP 明确反对）
- ~~WS subprotocol~~（否决）：WKWebView 支持有历史 bug，且滥用规范语义
- HTTP 图片端点（§8.1）**绝不用 query 传长期 token**，改用短时签名 URL（5 分钟有效）

**Origin 白名单**（必须显式配置，三种客户端 origin 不同）：

| 客户端 | Origin |
|---|---|
| 桌面 Electron renderer | `file://` 或 `app://` |
| 手机浏览器 | 反代 host（如 `https://xyz.example.com`） |
| Capacitor iOS | `capacitor://localhost` |
| Capacitor Android | `http://localhost`（或自定义 scheme） |

`verifyClient` 必须显式允许 `capacitor://localhost`——非 `http(s)` scheme 很多默认 CORS 配置不认。Capacitor 的 `capacitor://` scheme 下 cookie 行为异常，**不能用 cookie 传 token**。

**安全层次（自托管够用）**：WSS（反代 TLS 终止）+ token（首条消息校验）+ Origin 校验（防 CSRF，含 Capacitor scheme）+ 反代限流 + 未认证连接不纳入心跳/广播池。

### 6.1 核心设计原则

1. **客户端配置统一为「URL + token」**：不暴露反代/TLS 细节。反代是服务器侧的事，对客户端透明。
2. **runtime 不内置 TLS**：TLS 永远交给反代（公网）或 VPN overlay（Tailscale）。runtime 内置 TLS 是独立复杂度（证书加载/SNI/续期），收益不抵成本。
3. **引导连接（Bootstrap）**：服务端一次性输出「连接字符串」，客户端复制粘贴即可完成首连，避免手敲长 token。

### 6.2 连接字符串（Bootstrap URL）

**三种形态，按推荐顺序**：

#### [1] Web 浏览器直达（推荐 · 最通用）

```
http://<host>:<port>/#token=<TOKEN>
https://<domain>/#token=<TOKEN>
```

- **手机/电脑浏览器地址栏直接粘贴** → 打开 Web 端 HTML → JS 读 `location.hash` 拿 token → 从 `location.host` 推导 WS 地址 → 自动连接
- **token 放 hash fragment**（`#token=...`）：不发给服务器、不进 access log、不被 Referer 泄露、JS 可读
- **Web 端和 WS 同源**（runtime `--serve-web` 内置静态服务，§6.6）：Web HTML 从 `<host>:<port>` 加载，WS 地址自动推导为 `ws://<host>:<port>`，URL 里不需带 WS 地址
- 连接成功后 token 存 localStorage，后续直接访问 `http://<host>:<port>/`（书签即可）

**示例**：
```
# Tailscale（plain HTTP，WireGuard 加密）
http://myserver.tail-7c3a.ts.net:3210/#token=a3f8b2c1d4e5...

# 公网反代（HTTPS）
https://xyz.example.com/#token=a3f8b2c1d4e5...

# 局域网 IP
http://192.168.1.42:3210/#token=a3f8b2c1d4e5...
```

#### [2] APP 一键连接（需装 APP）

```
xyz-agent://connect?url=<WS_URL>&token=<TOKEN>
```

- PC/Mac APP：点击/粘贴到浏览器地址栏，唤起 APP 并自动填充
- 手机 APP（Capacitor）：扫码（QR 内容 = 此 deep link）或 deep link 唤起
- URL 参数需 `encodeURIComponent` 编码

#### [3] 手动填写（URL + Token 分开）

```
URL:   ws://myserver.tail-7c3a.ts.net:3210
Token: a3f8b2c1d4e5...
```

- Web 端提供「粘贴连接信息」输入框（支持三种格式解析）
- 备选路径（前两种都失败时的兜底）

**三形态分工**：

| 形态 | 手机浏览器 | 桌面浏览器 | 桌面 APP | 手机 APP |
|---|---|---|---|---|
| [1] 浏览器直达 | ✅ **推荐** | ✅ 推荐 | — | — |
| [2] APP deep link | — | — | ✅ 推荐 | ✅ 推荐（扫码/点链接） |
| [3] 手动填写 | ✅ 兜底 | ✅ 兜底 | ✅ 兜底 | ✅ 兜底 |

**为什么 [1] 是首选**：不用装 APP、不用手动填、地址栏直接粘贴即用。手机浏览器场景的最短路径。微信转发也走这个（微信不会拦 HTTP URL）。

### 6.3 服务端首启输出（一键复制）

runtime 首次启动（检测到 `~/.xyz-agent/token` 不存在）自动生成 token，终端输出：

```
╭────────────────────────────────────────────────────────╾
│  xyz-agent server started
│
│  ── 复制下面任一内容，粘贴到客户端即可连接 ──
│
│  [1] 浏览器直达（手机/电脑浏览器地址栏直接粘贴）:
│  http://myserver.tail-7c3a.ts.net:3210/#token=a3f8b2c1d4e5...
│
│  [2] APP 一键连接（已装 APP · 点击或粘贴到地址栏唤起）:
│  xyz-agent://connect?url=ws%3A%2F%2Fmyserver.tail-7c3a.ts.net%3A3210&token=a3f8b2c1d4e5...
│
│  [3] 手动填写（粘贴到 Web 端输入框）:
│      URL:   ws://myserver.tail-7c3a.ts.net:3210
│      Token: a3f8b2c1d4e5...
│
│  ── 二维码（手机扫码 · 内容为 [1] 的浏览器直达 URL）──
│  [▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓]
│  [▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓]   ← 手机浏览器扫码直接打开 [1]
│  [▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓]      （装了 APP 则扫 [2] 的 deep link QR）
╾────────────────────────────────────────────────────────╯
```

**QR 内容的选择**：
- 默认打印 **[1] 浏览器直达** 的 QR（手机浏览器扫码直接打开，零门槛）
- 装了 APP 的用户可请求 **[2] deep link** 的 QR（`--qr deep-link`，扫码唤起 APP）

**可达 URL 自动探测**（启发式，按优先级）：

1. `XYZ_AGENT_PUBLIC_URL` env（用户显式指定，反代场景必填，如 `https://xyz.example.com`）
2. Tailscale IP 探测：检查 `tailscale0` 网卡，或调 `tailscale status --json` 取 self 的 TailscaleIP（`100.x.x.x`）
3. Tailscale MagicDNS 名（`<hostname>.<tailnet>.ts.net`，需 MagicDNS 开启）
4. 局域网 IP（取非 loopback 的 IPv4）
5. fallback：`localhost:<port>`

探测到的是 **HTTP/HTTPS host**（用于 [1] 浏览器直达），WS 地址由 Web 端从 `location.host` 推导（同源，§6.6）。`XYZ_AGENT_PUBLIC_URL` 的 scheme 决定后续：
- `http://` / `https://` → Web 同源托管场景（[1] 可用）
- `wss://` → 仅 WS 反代、Web 另部署场景（[1] 需额外配 Web host，否则只能走 [2]/[3]）

**探测顺序的设计意图**：Tailscale 优先于局域网 IP，因为 Tailscale 跨网络可达（手机 4G 也能连），局域网 IP 只在同一个 WiFi 下有效。如果检测到 Tailscale，默认输出 Tailscale URL。

**多 URL 输出**（可选，`--print-all-urls`）：同时输出 Tailscale + 局域网 + 公网（如配了 `XYZ_AGENT_PUBLIC_URL`），让用户选。默认只输出探测到的最优一个。

### 6.4 客户端连接流程

**手机浏览器（最短路径）**：
```
1. 服务端终端复制 [1] 的 HTTP URL（含 #token=...）
   例：http://myserver.tail-7c3a.ts.net:3210/#token=a3f8b2c1...
2. 手机装 Tailscale（加入同一 tailnet），手机浏览器地址栏直接粘贴 URL
3. 浏览器：
   - DNS 解析 myserver.ts.net（MagicDNS）
   - HTTP GET / 拿 Web 端 HTML（runtime --serve-web 内置静态服务）
   - JS 读 location.hash 拿 token
   - 从 location.host 推导 WS 地址（ws://myserver...:3210，同源）
   - 自动连接（首条消息鉴权）
4. 连接成功，token 存 localStorage，进入 Web 端界面
5. 后续直接访问 http://myserver...:3210/（书签即可，不用再带 token）
```

**桌面/电脑浏览器**：同手机浏览器，复制 [1] 粘到地址栏即可。

**桌面 APP（Electron）**：
```
1. 首次打开 APP → 欢迎屏「连接服务器」入口
2. 用户复制 [2] 的 xyz-agent:// 链接（或 [1] HTTP URL，APP 都能解析）
3. APP 检测剪贴板格式（启动时 + 窗口聚焦时）：
   - 命中 xyz-agent://connect?... → 解析 WS URL + token
   - 命中 http(s)://.../#token=... → 从 host 推导 WS URL + 从 hash 取 token
4. 显示「检测到连接信息」→ 用户点「连接」→ 发起 WS + 首条 auth 消息
```

**Web 网页端（兜底 · 手动粘贴框）**：
```
1. 浏览器打开 Web 端 URL（无 #token，或 token 失效）
2. 首屏「粘贴连接信息」输入框，支持粘贴 [1]/[2]/[3] 任一格式：
   - http(s)://.../#token=... → 从 host 推导 WS URL，从 hash 取 token
   - xyz-agent://connect?... → 解析 WS URL + token
   - "URL: ws://... Token: ..." 多行 → 解析两行
3. 显示「检测到连接信息」→ 点「连接」
```

**手机 APP（Capacitor）**：
- 方式 A：**扫码**（服务端终端 QR）——扫 [1] 的浏览器直达 URL QR → 打开内置 WebView 加载该 URL（APP 内浏览器）；或扫 [2] 的 deep link QR → 唤起 APP 原生界面
- 方式 B：**微信收 URL → 复制 → 打开 APP**——APP `appStateChange` 回前台读剪贴板，命中 HTTP URL 自动提示「在 APP 内打开？」
- 方式 C：**deep link**——微信里点 `xyz-agent://` 链接直接唤起 APP 原生界面

**剪贴板探测的安全约束**（桌面 APP / 手机 APP 适用）：
- 只在「未连接」状态下探测（已连接的客户端不打扰）
- 探测到后**不自动连接**，必须用户点「连接」确认（防止恶意剪贴板自动触发）
- 解析失败静默忽略，不报错

**Web 端 token 存储**：连接成功后 token 存 `localStorage`（key 带 host 前缀，支持多服务器），下次访问同源 Web 端自动读取免重输。清浏览器数据会丢失，需重新粘 [1] URL。

### 6.5 四种网络拓扑的服务器侧配置

#### 形态 A：局域网直接 IP（无反代，无 TLS）

适合家庭/办公室受信网络。

| 项 | 配置 |
|---|---|
| runtime 启动 | `--host 0.0.0.0 --port 3210` |
| TLS | 无（plain `ws://`） |
| 防火墙 | 开放 3210 端口给局域网段 |
| 客户端 URL | `ws://192.168.1.100:3210` |
| token 传输 | 终端 QR + 引导字符串 |

**风险**：token 和消息明文走局域网。受信网络可接受；公司/公共 WiFi 不行。

#### 形态 B：公网域名 + 反代 + TLS（公网推荐）

| 项 | 配置 |
|---|---|
| runtime 启动 | `--host 127.0.0.1 --port 3210`（**只本地**，不暴露公网） |
| TLS | 反代做 TLS 终止 + Let's Encrypt |
| 反代监听 | 443（标准 WSS 端口） |
| 反代转发 | `wss://domain` → `ws://127.0.0.1:3210` |
| 防火墙 | 只开 22/80/443，3210 不对外开放 |
| 客户端 URL | `wss://xyz.example.com` |
| `XYZ_AGENT_PUBLIC_URL` | `wss://xyz.example.com`（让服务端输出正确的引导 URL） |

**nginx 最小配置**（必须，否则 WS 会断/被缓冲）：
```nginx
location / {
    proxy_pass http://127.0.0.1:3210;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
    proxy_read_timeout 3600s;   # 默认 60s 会砍长连接
    proxy_send_timeout 3600s;
    proxy_buffering off;         # 否则 pi 流式输出会被缓冲
}
```

**caddy 更简单**（自动 Let's Encrypt）：
```
xyz.example.com {
    reverse_proxy 127.0.0.1:3210
}
```

#### 形态 C：公网直连 runtime（不推荐）

| 项 | 配置 |
|---|---|
| runtime 启动 | `--host 0.0.0.0 --port 3210` + 公网防火墙开放 |
| TLS | 需 runtime 内置（**当前不支持，需新增独立工作量**） |

**不建议做**。公网暴露就走形态 B（反代）。理由：
- runtime 内置 TLS 是独立复杂度（证书加载、续期、SNI、HTTPS 端点）
- runtime 直接暴露公网，没有限流/防护层，安全面差
- 反代已是公网部署的工业标准

如用户坚持直连，让 runtime 跑 plain WS + 用户自己用 `stunnel` / `caddy file_server` 等外挂 TLS。

#### 形态 D：Tailscale（个人多设备最优解）

**主要使用场景**。Tailscale 个人免费版支持最多 100 台设备，跨网络安全访问，WireGuard 端到端加密。

| 项 | 配置 |
|---|---|
| runtime 启动 | `--host 0.0.0.0 --port 3210`（或绑 `tailscale0` 接口） |
| TLS | **无（plain `ws://`）**——WireGuard 隧道已端到端加密 |
| 防火墙 | Tailscale ACL 控制谁能连 |
| 客户端 URL | `ws://<server>.tail-scale.ts.net:3210`（MagicDNS）或 `ws://100.x.x.x:3210`（Tailscale IP） |
| 客户端前置 | **每个客户端装 Tailscale 客户端并加入同一 tailnet** |

**优势**：
- 零 TLS 配置（WireGuard 加密）
- 没有反代复杂度
- 比公网暴露安全得多（Tailscale ACL + 设备级认证 + tailnet 锁定）
- 跨网络（手机 4G 也能连家里的服务器，走 DERP 中继或直连）

**Tailscale 部署要点**：
1. 服务器装 Tailscale：`curl -fsSL https://tailscale.com/install.sh | sh && tailscale up`
2. 开启 MagicDNS（admin 控制台 → DNS → Enable MagicDNS）
3. ACL 配置（admin 控制台 → Access Controls）限制只能 tailnet 内访问 3210：
```json
{
  "acls": [
    {"action": "accept", "src": ["*"], "dst": ["*:3210"]}
  ]
}
```
4. runtime 启动时自动探测 Tailscale IP/MagicDNS 名输出到引导字符串

**代价**：每个客户端设备都要装 Tailscale。iOS/Android 商店装 Tailscale 客户端 + 登录同一账号即可。

### 6.6 Web 网页端托管

Web 网页端是静态 SPA，托管位置灵活：

| 方案 | 说明 | 适用 |
|---|---|---|
| **runtime 内置静态服务**（推荐默认） | runtime 启动 HTTP server 托管前端 dist + WS，同端口同源 | 局域网/Tailscale 最省事，不用额外配；**[1] 浏览器直达可用** |
| **反代同站托管** | nginx 同时托管静态前端 + 反代 WS（`/` 走静态，`/ws` 反代 runtime），同域名同源 | 公网场景，一个域名一个端口，TLS 统一；**[1] 浏览器直达可用** |
| **独立部署** | Web 前端部署到 Vercel/Cloudflare Pages/任意静态 host，与 WS 跨源 | 前端独立迭代；[1] 不可用（host 不对应 WS），只能走 [2]/[3] |

**推荐**：
- **局域网/Tailscale**：runtime 内置静态服务（`--serve-web <dist-path>`），一个进程搞定前端 + WS
- **公网**：反代同站托管（一个域名同时拿到前端 + WS，TLS 统一）

**同源 bootstrap 逻辑**（[1] 浏览器直达的核心）：
- Web 前端和 WS 同源（同 host 同 port）时，浏览器加载 HTML 后 JS 从 `location.host` 推导 WS 地址，URL 只需带 token（放 hash fragment）
- 推导规则：
  - `http://host:port` → `ws://host:port`
  - `https://host` → `wss://host`（标准 443 省略）
  - `https://host:8443` → `wss://host:8443`
- 因此服务端只需输出一个 HTTP URL `http://<host>:<port>/#token=...`，浏览器地址栏粘贴即可，**用户无需理解 WS 概念**

**跨源场景（独立部署 Web）的妥协**：
- Web 前端在 `https://web.app.com`，WS 在 `wss://api.server.com`：浏览器 WS 握手带 `Origin: https://web.app.com`，服务端 Origin 白名单要放行
- [1] URL 失效（host 不对应 WS），只能走 [2] deep link 或 [3] 手动填 WS 地址
- 不推荐除非前端独立迭代是硬需求

### 8.4 协同改造（阻断点修复）

#### P0 — clientId 通道 + 首条消息鉴权（解锁一切的前提）

握手协议（首条 WS 消息携带）：
```
客户端连接: new WebSocket(url)  // URL 不带敏感参数
连接建立后发送首条消息:
  { type: 'auth', token, clientId, deviceName, lastSeq }
```

clientId 由客户端本地生成（uuid 或稳定设备标识），持久化在客户端本地。deviceName 用户可设置。

runtime 侧：
- `connection-manager.ts`：`Set<ws>` → `Map<clientId, ConnectionCtx>`，ConnectionCtx 含 `{ws, clientId, deviceName, connectedAt, authenticated}`
- 首条 auth 校验通过前，连接 `authenticated=false`，不纳入心跳/广播池，超时（如 5s）未发 auth 则 close(4001)
- `ConnectionCallbacks` 接口：onConnect/onMessage/onDisconnect 签名加 clientId
- 所有 handler 拿到的 ctx 增加 `clientId` 字段

#### P1 — 操作互斥升级（租约锁）

当前 `message-dispatcher.ts:93-100` busy 拒绝是无差别广播 + 简陋布尔标志。升级为**带 TTL 的租约锁**：

```
客户端 A 发消息（pi 开始生成）:
  → runtime 发放租约: session.lease = { owner: A, ttl: 30s, renewedAt }
  → 广播 session.busy { sessionId, clientId: A, deviceName: "Mac" }
  → 所有客户端 UI 显示「Mac 正在与 Agent 对话...」

A 心跳续租（流式期间持续）: ping loop 续租 TTL

租约 TTL 到期（A 崩溃/断网）:
  → runtime 自动释放租约，广播 session.idle { sessionId, reason: 'lease_expired' }
  → 其他客户端可抢占

客户端 B 此时发消息:
  → send.rejected { reason: 'busy', busyOwnerId: A, busyOwnerDevice: "Mac", leaseExpiresAt }
  → 只回给 B（reply，不广播，P5 C4 投递语义变更）
  → B 看到「Mac 正在操作，请稍候」
```

session 状态（`types.ts:26-85` IManagedSessionView）增加 `busyOwnerId` / `leaseExpiresAt` 字段。**【审查 M1/R4-M1】~~fencing token~~ 推迟到真正消费方**：原计划 fence（leaseFence 字段），但 P5-P7 无消费方（P6 config CAS 用独立 version），按 YAGNI 推迟到真有「跨客户端因果序」需求时。详见 P5 spec D3。

#### P2 — 并发保护扩展（git/file/config/worktree/terminal）

除 pi 外的写入型操作当前全裸奔。按 per-resource 加操作队列：

| 资源 | 当前问题 | 对策 |
|---|---|---|
| git | `commit` 是 TOCTOU（先 status 再 commit），并发抢 `index.lock` | per-cwd git 操作 mutex（串行化所有 git 命令） |
| config | last-write-wins 静默覆盖 | 带 version 的 CAS（client 带期望 version，冲突则拒绝） |
| worktree | 同名分支并发一个失败 | in-flight 去重（同名分支创建串行化） |
| session metadata | rename/delete 与 switch 并发报错 | 删除前广播 `session.deleting`，让其他客户端先收起 panel |
| terminal resize | 多客户端最后生效冲突 | per-session resize owner + 协商（取最小客户端或 owner 优先） |
| terminal write | 多客户端字符交错 | 接受（终端协同常见行为），加 presence 提示「X 正在输入」 |
| terminal scrollback | 重连/新连入看不到历史 | attach 时回灌 ring buffer 最近 N 行（当前 attach 是 no-op） |

#### P3 — pi 与连接生命周期解耦

**语义决策**：pi 与 WS 连接解耦，客户端断开时 pi 继续跑到完成或显式取消（AI agent 远程化必需，业界共识）。

实现要点：
- runtime 侧：WS 断开不触发 pi kill；pi 跑到 turn_end 后正常落 JSONL，下次 restore/`getFullHistory` 可拉到完整结果
- 客户端重连：短断线靠 P2 的 lastSeq + per-session ring buffer 回放拉断线期间的广播消息；长断线/buffer 驱逐/runtime 重启靠 P2 的 `seqReset → location.reload()` 冷启动全量重建兜底（renderer 无全局 reset 能力，reload 是构造性正确路径）
- 审批挂起场景：pi 等审批/输入时所有客户端离线 → pi 挂起等待（带超时），任一客户端重连后用 presence 唤醒；未来可叠加推送通知（P7+）

#### P4 — 插件活跃 session 的 per-client 化

`plugin-service/api/session-api.ts:33-67` `ActiveSessionResolver` 当前返回 runtime 全局唯一 active session。改造：resolver 绑 clientId，从 `activeSession: Map<clientId, sessionId>` 取。

#### P5 — 远程删除 session 的多客户端清理

当前 `session.delete` 只广播列表（`broadcastSessionList`），其他客户端 panel 的 store 分区清理依赖本地流程。补充：

```
客户端 A 删 session X:
  → 广播 session.deleted { sessionId: X }  // 单独事件，不只靠列表 diff
  → 所有客户端监听后: 强制收起 X 的 panel + 调 clearSession(X) 清 store 分区
```

#### P6 — 前端协同感知（presence）【R4-M2：presence 已移到 P5，本节拆分】

**【R4-M2 修正】presence 相关（stores/presence.ts、presence.update、session.busy/idle）已移到 P5**（因 isOperating 依赖 lease，P5 做 lease 时一并做更内聚）。本节剩余项归 P6：

- `session.deleted`：session 被删除（P6 D6，从 reply 升级为 broadcastExcept 广播）
- `session.deleting`：session 即将删除（P6 D6，给其他客户端收起 panel 的机会）

P5 落地的 presence（参考用）：
```ts
// stores/presence.ts（P5 新增）
interface PresenceState {
  connections: Array<{
    clientId: string
    deviceName: string
    activeSessionId: string | null
    isOperating: boolean  // 持有某 session 的 pi 租约
  }>
}
```

WS 事件归属：`presence.update`/`session.busy`/`session.idle` → **P5**；`session.deleting`/`session.deleted` 广播 → **P6**。

UI 显示：sidebar 底部「在线设备」列表（P5）、session 标题旁的占用指示器（P5）、session 被删时 panel 收起（P6）。

## 十、待确认事项

1. **协同强度**：默认按「看共享 + 操作互斥」走（pi 单例物理约束）。若要「并发操作」（pi 内部排队），需 pi 适配层改造，复杂度更高。
2. **身份模型**：默认按「单用户多设备」走（token 即身份）。若要「多用户账号体系」，需额外加用户管理。
3. **pi 与连接生命周期解耦**：默认按「pi 继续跑」走（业界共识）。需确认：(a) 客户端断开时 pi 继续到 turn_end 还是立即 kill；(b) pi 等审批时所有客户端离线，是挂起等待还是超时取消。

   > ✅ **已决（P3）**：(a) 断开后 pi 继续跑到 turn_end（D1，固化为契约 + 防回归测试，无 onDisconnect 清理路径）；(b) 审批挂起时全客户端离线 → 无限期挂起等待，**不设超时**（D2），任一客户端重连时服务端主动补发 `extension.pendingRequestsBatch` 唤醒（D3）。详见 [.xyz-harness/2026-07-26-remote-p3/spec.md](../../.xyz-harness/2026-07-26-remote-p3/spec.md) §一决策表 D1/D2/D3。
4. **pi Linux 兼容性**：pi 二进制是否有 Linux 版本？musl/glibc 兼容问题？需 P0 阶段实测确认。
5. **推送兜底是否做**：iOS/Android 后台冻结是 OS 硬约束，不配 FCM/APNs 则 APP 进后台失联。自托管 + 个人使用场景下，是否接受「必须前台才实时」？还是必须做推送（P12）？
6. **文件上传/下载是否做**：远程化后客户端无法把本地参考文档喂给 pi，也无法下载 pi 产物。是否纳入本期范围（P13）？还是后续再说？

8. **多 pi session 资源占用**：服务器跑多个 pi 实例的内存/CPU，`XYZ_AGENT_MAX_SESSIONS` 默认值需 P0 阶段压测确定。

## 十二、已知技术风险与对策

### 12.1 移动端 WS 稳定性（硬约束，不可绕过）

**OS 行为**：iOS WKWebView 后台停止 JS 执行（心跳 `setInterval` 失效），~30s 后 socket 被 kill；Android 后台联网限制类似。这是 OS 设计不是 bug。

**对策分层**：

| 场景 | 对策 |
|---|---|
| 前台正常使用 | 心跳 < 25s（短于蜂窝 NAT 30s）+ pong 超时校验 |
| 短暂断线（切网络/进电梯） | 指数退避重连（无 60s 上限）+ lastSeq 拉缺失 |
| APP 切后台 → 回前台 | Capacitor `appStateChange` 监听，active 时强制重连 + 全量同步 |
| APP 长期在后台 | FCM/APNs silent push 唤醒（P12 可选） |

**反代超时坑**（部署必须配置）：
- nginx 默认 `proxy_read_timeout` 60s（与心跳 45s + ping 15s 边界很紧）
- Cloudflare Free/Pro 硬性 100s 空闲超时（仅 Enterprise 可调）
- nginx `proxy_buffering` 不关会缓冲 pi token 流和 terminal 输出 → 几秒看不到东西
- 部署文档必须给最小配置：`proxy_read_timeout 3600s`、`proxy_buffering off`、`Upgrade`/`Connection: upgrade` 透传

### 12.2 多客户端并发冲突

**问题**：除 pi 外，git/file/config/worktree/terminal 的写入操作原本全裸奔。多客户端并发 → TOCTOU、抢锁、静默覆盖。

**对策**（§8.4 P2/P5/P6，**均已实现**）：

| 资源 | 对策 | 实现阶段 | 实现位置 |
|---|---|---|---|

### 12.3 token 安全

**风险**：token 在 query string 会进反代 access log、浏览器 history、Referer（OWASP 反对）。

**对策**（已纳入 §五）：WS 首条消息鉴权（全平台兼容 + 不进日志）；HTTP 图片端点用短时签名 URL（5 分钟）。

**Capacitor Origin**：iOS 是 `capacitor://localhost`，Android 是 `http://localhost`。服务端 Origin 白名单必须显式包含这些 scheme。`capacitor://` scheme 下 cookie 不可靠，不能用 cookie 传 token。

### 12.4 服务端目录树 RPC 越权

**问题**：`pickDirectory` 替代需列服务器任意目录，但现有守门是 session-cwd 作用域。

**对策**（§8.1）：新 RPC `dir.list` 独立 allow-root（`$HOME` 或 `XYZ_AGENT_PROJECT_ROOTS`），防止浏览 `/etc`、`/home/*`。单用户自托管下严重性低，但仍需做。

### 12.5 跨客户端消息顺序

**现状**：单连接内顺序由 Node 单线程保证，跨客户端无严格总序。

**短期接受**：偶发"我和另一台设备看到的对话流顺序不一致"，影响轻。

**长期方案**（如需）：引入全局 fencing token + 跨客户端因果序。**【R4-M1 修正】原计划留作 P5 租约锁的延伸，但 P5 审查 M1 发现 P5-P7 无 fence 消费方（P6 config CAS 用独立 version），按 YAGNI 推迟到真正需要跨客户端因果序时再设计**。当前不预先做。
