## 详细论证（仅 MUST_FIX 与关键 SUGGESTION）

### MF-1 ｜ 03-§3.D8 Step③ ｜ VALID_TOOL_MODES「改 import shared」阻断性事实错误

**文档声明**（§3.8.1）：「`VALID_TOOL_MODES` 等枚举是 shared 层同语义的本地副本（:40-48 注释自认『shared 同语义』）」。Step③（§3.8.3）：「`VALID_TOOL_MODES` 等枚举改 import shared（:40-48 本地副本删除）」。

**源码核实**（`grep -rn "VALID_TOOL_MODES" packages/shared/src/` → exit 1，零命中）：
- shared **根本不导出** `VALID_TOOL_MODES`。
- `preset-service.ts:40` 的 `VALID_TOOL_MODES` 定义**没有**任何 shared 相关注释（就是一行 `const VALID_TOOL_MODES = [...]`）。
- 真正带「shared 同语义」注释的是 `:46` 的 `VALID_EXTENSION_MODES`，且该注释明确写：「shared 层 pi-preset.ts 的 `EXTENSION_MODES` **未导出（私有）**，此处本地定义副本」。

**问题**：文档把两个不同枚举（`VALID_TOOL_MODES` 无 shared 对应 vs `VALID_EXTENSION_MODES` 对应 shared 私有 `EXTENSION_MODES`）混为一谈，并据此声称「改 import shared」。但 shared 既无私有副本也无可导入项——**Step③ 无法执行**。

**修复方向**：核实 shared 哪些枚举真导出；若 `VALID_TOOL_MODES` 确需收敛，D8-③ 必须增加「先在 `shared/src/pi-preset.ts` 创建并 `export` 该枚举」前置子步骤，而非直接「改 import」。

### MF-2 ｜ 03-§3.D1 §3.1.3 ｜ 守护完整性言过其实（bypass 路径未承认）

**文档声明**：§3.1.3「type-only 必须拦（3 处 PiXxx 泄漏全是 type-only，只拦值导入守护即失效）」；§4-D1-1 验收用 `import type { PiSessionEntry }` 探针验证。三条规则均基于「import 语句正则」。

**对抗式攻击**——守护基于正则解析 `import` 语句，以下三类**合法 TS/JS 写法**绕过全部三条规则，且 §4 验收未探针：

1. **`export { PiSessionEntry } from '../../infra/pi/pi-protocol.js'`**（barrel re-export）。这不是 `import` 语句，正则不命中。这是**最可能的意外 bypass**——有人为「方便」在 services 建类型 barrel 文件时发生。
2. **`const x = require('../../infra/pi/pi-protocol.js')`**（CJS require）。运行时同样跨层，正则不命中。
3. **动态 `import('../../infra/pi/pi-protocol.js')`**。

**严重性判定**：当前 9 处泄漏全是静态 `import`，守护能拦住**当下问题**——守护不是无用。但文档从「3 处 PiXxx 全是 type-only」推出「type-only 必须拦」的完整性诉求，显示作者在意覆盖完备；却未承认上述 bypass 类，且 §4 探针只测 `import`/`import type`。这给后续维护者虚假信心（「我们有 pre-commit 守护，跨层泄漏会被拦」）。同时文档明确拒绝 AST（「不引入完整 AST 依赖」），却又想要完备性保证——存在工具能力与目标诉求的张力。

**修复方向**（二选一）：
- (a) 诚实降级：文档显式标注「best-effort 静态 `import` 扫描，不覆盖 re-export/require/动态 import」，把守护定位为「拦住已知回潮模式」而非「架构边界完整守卫」；
- (b) 低成本补强：正则同时匹配 `export … from`（与 `import` 同构，一行正则成本），把最可能的 barrel bypass 堵上；require/动态 import 因罕见可记入已知限制。

### MF-3 ｜ 03-§3.D1 §3.1.3 ｜ 白名单粒度与例外清单失配（双 SSOT 无同步）

**文档声明**：§3.1.3「白名单 = `runtime-three-layer-design.md` 受控例外清单的机器可读版：`infra/logger.js`、`infra/pi/pi-paths.js`、`infra/git/git-status-parser.js`、`infra/fs/ignore-parser.js`（例外清单 SSOT 放脚本头部常量，与 three-layer-design.md 双向注释互指）」；并引用 `check_env_whitelist_sync.py` 的 SSOT 先例。

**源码核实**（`docs/architecture/runtime-three-layer-design.md:156-200`）：例外清单是**文件级**——
- ① logger：列出**8 个具体文件:行**（quota-cache:15、quota-service:21、codex-parser:23、minimax:14、mimo:13、opencode:13、kimi:11、worktree-config-helper:23）
- ② pi-paths：列出**6 个具体文件:行**
- ③ 纯解析函数：列出 **2 个具体文件:行**

而脚本白名单是**模块级**（4 个模块路径，任意 services 文件均可 import）。

**失配后果**：这是两套**不同粒度的策略**，不是「机器可读版」关系：
- 新增一个 services 文件 import `logger` → 脚本放行（模块级允许），但违反文档文件级清单（该文件不在 8 个 enumerated 文件内），文档清单需手工补——**必然漂移**。
- 文档声称「双向注释互指」恰恰制造了**两个 SSOT**，且无同步检查。这违背它自己引用的 `check_env_whitelist_sync.py` 先例——后者正是用脚本强制 `ENV_WHITELIST_PREFIXES` 只在 `shared/constants.ts` 单点定义，防止 SSOT 退化。

**修复方向**（二选一）：
- (a) 脚本白名单改**文件级**：枚举允许的 `(services 文件, infra 模块)` 对，与文档清单严格对应，并加同步检查（脚本读文档清单 / 文档引用脚本常量）；
- (b) 文档清单**降级为模块级**：删除文件:行枚举（logger 8 处、pi-paths 6 处…），声明「services 层可 import 这 4 个 infra 模块，不约束具体文件」，与脚本对齐。注意 (b) 会丢失「新增 logger 消费方需登记」的审计能力——需显式取舍。

### MF-4 ｜ 03-§3.D6 ｜ JSON_INDENT 重复处数低估

**文档声明**：§3.6.1「`JSON_INDENT` 常量在 4 个新文件各自重复」；§3.6.3 step1「`rg "JSON_INDENT" … 定位 4 处重复定义」。

**问题**：「4 处」低估约 2 倍。收敛方向正确（收 `utils/json-store.ts` 单点导出），但 scope 与工作量评估偏差。修复：重跑 grep 更新数字。

### MF-5 ｜ 03-§3.D1 Step4 ｜ IConfigStore 行号错误
