现状 vs 目标 · 本 spec 描绘目标态 当前实现度见下

现状（pi-extension 已完整）

pi-extension 渲染机制完整可用：M4/M5/M7/M8/M11/M15 挂载点已落地，走 details.__gui__ + extension:widget + extension:status + extension.ui_request。

plugin-sdk 渲染面完全空白：contributes.panels / statusBarItems / views 零消费；plugin:viewUpdate 消息族未实现；ViewHost / ContributionRegistry / ExtensionHost 在 renderer 不存在。

目标（统一扩展架构）

统一扩展架构：对齐 renderer-target-architecture.md，pi extension + plugin 共用 GuiComponent 7 原语 + 统一 GuiComponentRenderer。

ExtensionHost 层消费：新增 ExtensionHost 消费 plugin contribution（views/menus/statusBarItems/commands/configuration），统一注册到 ContributionRegistry，由 ViewHost 驱动渲染。

挂载点机制澄清：挂载点是「数据驱动渲染」——plugin 推数据（原语树 / 元数据），renderer 渲染，不是同步 hook。
hook（before/after/阻塞/修改数据）作用在 tool / message 层（拦截、改写、阻塞 tool call 或消息），不作用在渲染挂载点——渲染挂载点只接受数据，不接受控制流。

决策变更 · 全局底栏 → main-panel 局部 2026-07-31 推翻原方案
原方案：AppShell 底部跨 sidebar+main+drawer 全宽细条（bg-bg-sunken，VSCode 风格全局状态栏）。
现方案：M8 挂 main-panel 内、composer 下方，不跨 sidebar/drawer。
理由：① status 信息语义上属于「当前对话/agent 状态」，跟着 main-panel（对话主体）走比跨全宽更内聚；② sidebar 是导航区、drawer 是辅助区，往那里渗 status 语义不符；③ 全局底栏的 VSCode 范式适合「编辑器全局状态」，xyz-agent 是多 panel 对话工作台，每个 panel 独立 status 更合理（未来 split 多 panel 时各 panel 各自底栏）。
代价：drawer 关闭时 status 仍可见（在 main 底部），但 drawer 打开时 status 不延伸到 drawer 下方——drawer 自己的 footer 若需 status 另行处理。
§3

维度 B · 7 原语 v6 视觉（核心）

GuiComponent 是 pi extension + plugin 的共享渲染协议，7 个结构化原语（card / stats-line / progress-bar / list-tree / columns / tab-bar / ansi-text）替代 TUI ASCII 布局。这是最成熟、最核心的注入面（M4 tool result / M5 custom message / M7 drawer 内容）。v6 重设计 只改 CSS/模板，不改协议类型——已接入的 extension 零改动自动获得 v6 视觉。逐原语按 renderer-target-architecture §5.2 表定义 v6 目标。

9.2 plugin handler 注册（代码示例）manifest 声明 + activate 注册

两步：① manifest 声明按钮/command（renderer 渲染入口，§4）；② activate() 注册 handler（点击后执行逻辑）。handler 里的 ctx.api.xxx 调用 = 点击按钮后能干的事。这是 external plugin 扩展能力的唯一编程式入口（L3 custom 逃生口限 built-in）。

① manifest 声明（入口）json
// package.json · contributes
{
  "contributes": {
    "commands": [{
      "id": "my-ext.deploy",
      "title": "Deploy",
      "icon": "rocket",
      "keybinding": "mod+shift+d"
    }],
    "menus": {
      "composer.toolbar": [
        { "commandId": "my-ext.deploy" }
      ],
      "panel.header": [
        { "commandId": "my-ext.status" }
      ]
    }
  }
}
② activate 注册 handler（执行逻辑）typescript
export function activate(ctx: PluginContext) {
  ctx.api.commands.register('my-ext.deploy', async (args) => {
    // ① 读配置（M16）
    const env = await ctx.api.config.get('environment')
    // ② 弹确认框（M11 companion-band）
    const ok = await ctx.api.ui.showConfirm(
      'Deploy', `部署到 ${env}？`
    )
    if (!ok) return
    // ③ 改底栏状态（M8）
    await ctx.api.ui.updateStatusBarItem(
      'deploy-status', 'deploying...'
    )
    // ④ 推 view 内容（M2，GuiComponent 原语树）
    await ctx.api.views.update(
      'my-ext.pipelines', buildTree(result)
    )
    // ⑤ 往对话流发消息（M4，触发 agent turn）
    await ctx.api.sessions.sendMessage({
      role: 'user', content: '部署完成'
    })
  })
}
声明 vs 注册: manifest 声明「入口长什么样」（按钮位置/icon/commandId）；activate 注册「点击后干什么」（handler 函数）。两者解耦
handler 是异步的: async 函数，可 await 多个 SDK API 串联（读配置→弹框→执行→反馈）
多路反馈: 一次 handler 执行可同时更新底栏 / 推 view / 发消息 / 弹框——不限于触发它的挂载点
扩展方式: plugin 想加新能力 = 注册新 command + handler。外部用户装 plugin 即获得这些 command

9.4 当前缺口：闭环 vs 空壳 架构定义目标 · 代码未实现

16 挂载点分两类：完整闭环（声明入口 + handler 注册 + 内容推送全通）和声明式空壳（入口能声明渲染，但点击后无执行逻辑 / 无内容推送）。分类依据 = SDK API 实现状态。

✓ 完整闭环（5 挂载点）

入口 + 执行 + 反馈全通。这些挂载点 plugin 能真正「做交互」：

M4 tool result block · M5 custom message（__gui__ 推送）
M7 drawer widget · M8 底栏 status（updateStatusBarItem）
M11 companion-band（ask-user 及 confirm/select/input）

pi-extension 机制完整可用，plugin 经适配器复用。M15 已降级（仅致命错误），不计入完整闭环。

✗ 声明式空壳（6 挂载点）

入口能声明渲染（按钮/tab 出现），但点击后无 handler 执行 / 无内容推送：

M1 第5 tab · M2 二级 view tab（views.update 缺）
M9 composer 工具条按钮 · M12 panel header 按钮（commands.register 缺）
M14 独立 view · M16 settings schema（声明渲染但无 handler）

contribution 已声明，renderer 零消费 handler。

注：M3/M6/M10/M13 为低优/未来扩展/已闭环（slash command M10 走 session.commands 双轨已通），不在此二分。
必修缺陷 · 点击闭环前置任务（renderer-target-architecture §9.2） 主干化前置
缺口 1 · api.commands.register：CommandRegistry（§6 ExtensionHost 目标态）未实现。plugin 无法注册 command handler → M9/M12 按钮点击落到 fire-and-forget ack（plugin.executeCommand 返回 pong {}，无执行）。
缺口 2 · api.views.update / provide：ViewHost + plugin:viewUpdate 消息族未实现。plugin 无法往 M2/M7/M14 推 GuiComponent 内容 → view tab 点开是空的。
修复方向：renderer 新增 ExtensionHost 层（ContributionRegistry + CommandRegistry + ViewHost + MessageBusBridge），消费 plugin contribution 并驱动渲染分发。详见 renderer-target-architecture.md §6。
阶段归属（D4）：ExtensionHost/API 缺口属架构路线，本 spec 描绘目标态，不在阶段 A 落地，阶段 B 衔接（design L1.3 已登记）。
缓解：5 个完整闭环挂载点（M4/M5/M7/M8/M11）已能覆盖大部分交互场景（tool result / 自定义消息 / 底栏 / 弹框）。M15 降级为仅致命错误，不计入完整闭环。声明式空壳的 6 个是「入口已画好，等接线」。
